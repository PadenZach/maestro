# v0.5.0 Offline application observability

Status: Draft for discussion. Implementation and the release version bump belong
in a separate change.

Maestro should retain previously connected applications and their last observed
workflow data so users can investigate applications that scale to zero. Offline
views must show when data was collected and where information is missing.

> As a Maestro user with DBOS applications that scale to zero, I want to inspect
> application state, logs, and errors while an application is offline so I can
> debug failures and understand what happened.

## Requirements

- Keep previously connected applications discoverable for a defined retention
  period, including across Maestro restarts when retained storage is available.
- Support offline workflow and step inspection using saved observations.
- Preserve gateway ownership of authentication, RBAC, and tenant isolation.
- Keep storage modular, with one initial backend and room for another adapter
  such as Postgres without changing the UI or collection logic.
- Keep the existing single active Maestro deployment model and executor-based
  reads. This feature does not require application database credentials.

## Current behavior

The [hub](../internal/hub/hub.go) removes an application when its last ready
executor disconnects. The [console](../internal/console/applications.go) and
[application API](../internal/api/registry.go) build their lists from those live
executors. Workflow reads require an executor, so retaining an application name
alone would not enable offline inspection.

The [protocol](../internal/protocol/types.go) uses requests and responses; it
does not push workflow changes or expose an application logger subscription.
Existing inspection data includes workflow and step errors, events,
notifications, and streams. Capturing stdout or an external logging service
would require a separate integration.

## Proposed user experience

The application list includes online and retained offline applications. Each
application shows its live executor count, last observed connection time, and
last successful data collection time. Persisted executor metadata never counts
as a live connection, including after a Maestro restart.

Opening an offline application shows its retained workflows. Workflow details,
steps, timelines, and payload panels remain navigable where data was captured.
Each saved view says "Last observed at …" and distinguishes unavailable,
expired, unsupported, and partially collected data from a successful empty
result. A saved running status means it was running when observed; it does not
assert that it is still running. Offline timelines stop at the observation time.

Live reads remain authoritative while an executor is available. Reconnection
refreshes saved observations. An SDK refusal, malformed reply, or validation
error must remain an error; saved data must not silently replace it. Proposed
automatic fallback is limited to an application with no ready executors.

Existing routes and successful workflow response shapes remain compatible.
Saved API responses need explicit source, observation time, and coverage
metadata, preferably through response headers where adding an envelope would
break clients. The exact header contract remains open. Missing retained data
while offline must not claim that a workflow does not exist in DBOS.

## Collection and coverage proposal

Collect through the existing executor read protocol while applications are
online, and save successful validated UI/API reads through the same observation
service. A bounded background collector makes inspection possible without
someone having opened each workflow first. Capture on disconnect alone cannot
work because the last executor is already unavailable.

The collector should discover recent workflows and revisit tracked unfinished
workflows, including those created before the recent discovery window. Fetch
details and paginated steps for the workflows within the collection budget.
Collection needs a polling interval, discovery window, and explicit work and
storage limits; their values are open decisions. A truncated scan or unsupported
SDK operation must produce visible coverage information. Collection must yield
to interactive reads and recovery work.

| Data | Proposed v0.5.0 treatment |
| --- | --- |
| Application identity and last executor metadata | Retain after a successful handshake; track liveness separately. |
| Workflow status, metadata, relationships, and errors | Collect for workflows within the chosen coverage policy. |
| Steps, timings, child references, and errors | Collect with pagination; disclose missing pages or children. |
| Workflow inputs/outputs and step outputs | Proposed inclusion for offline debugging; confirm payload policy and size limits. |
| Events, notifications, and streams | Proposed inclusion where supported; confirm collection and size limits. |
| Queue, schedule, and overview panels | Decide whether to retain in v0.5.0; otherwise show explicit offline unavailability. |
| Application stdout and structured logs | Scope decision; the current protocol has no log retrieval operation. |
| Arbitrary aggregates and workflow exports | Proposed exclusion from offline support in v0.5.0. |

Offline lists and searches operate on retained records and describe their
coverage. They must not present retained counts as complete DBOS totals. The
supported offline filters and pagination contract must be decided before
implementation; uncaptured query results cannot be manufactured by replaying an
unrelated cached response.

Polling preserves the last successfully observed state. It cannot guarantee a
final snapshot before scale-down, capture changes between polls, or observe
changes while disconnected. Requiring complete history would need an additional
data source or application cooperation and would change this scope.

## Storage and retention proposal

Introduce a small observation service used by the console, API, and collector.
Keep the hub responsible for live connections and RPC. Keep workflow recovery
and commands on the live path; retained data must never establish executor
availability or trigger a replay of a command.

The service owns capture, freshness, and retention rules. A narrow storage
interface supports application records, workflow observations and their detail
sections, listing, and expiry. Implement only the operations required by the
chosen offline views and one backend initially. Avoid a generic cache framework,
an event history store, or a new query language.

Key records by organization and application, then workflow and detail identity.
Executor IDs are ephemeral and must not define application identity. Storage
must be isolated between deployments that share a backend. Store capture times,
expiry, and field/page coverage with the data. Preserve opaque SDK payloads as
opaque values and retain the distinction between omitted fields and nulls.
An observation that omits payloads must not overwrite previously captured
payloads as null or make their older timestamps appear fresh. Late responses
must not replace a newer accepted observation.

SQLite is the proposed first backend for the existing single-instance model:
it requires [no separate database server](https://www.sqlite.org/zeroconf.html).
It would require persistent disk for survival across container replacement and
a Go driver compatible with the current release builds. Valkey is an alternative
for deployments preferring an external service; restart survival depends on its
[persistence configuration](https://valkey.io/topics/persistence/), and
[eviction](https://valkey.io/topics/lru-cache/) can remove data before its TTL.
Shared storage alone does not add support for multiple active Maestro instances.

Propose opt-in persistence. Separate the time an offline application remains
discoverable from the lifetime of its captured data: application retention runs
from its last observed connection, while data retention runs from collection.
Reads of saved data do not renew either TTL. Connected applications remain
visible even if every saved observation has expired. Expired data is excluded
at read time and removed through bounded cleanup. Specify capacity behavior as
well as TTL so a busy application cannot grow storage without bound. Expiring an
offline application also removes its retained data.

Storage failures must not interrupt healthy live reads, executor connections,
or recovery. Surface capture failures and lost coverage. An unreadable store
must produce an unavailable result rather than an empty application history.

## Gateway and access boundaries

Serve retained data through the existing application routes and their current
gateway policies. Do not add a separate history listener, public storage
endpoint, new identity scheme, or embedded RBAC. Organization validation,
application scoping, request validation, and payload selection apply before
any saved response is returned. Existing global discovery routes retain their
existing gateway protection.

Retain domain observations rather than authenticated HTTP responses. Do not
persist credentials, cookies, authorization headers, or SDK URL keys, and do
not log captured payloads. Background collection uses the existing app-scoped
executor connection. Workflow authenticated-user metadata is data, not an
authorization decision.

An explicit executor privacy refusal must never cause cached payloads to be
served as a successful substitute, including after a later disconnect. Decide
how a known restriction makes affected saved payloads unavailable until a fresh
permitted read. Persistence makes previously observed data last longer, so
payload retention and how an operator purges it need an explicit decision.
Gateway access revocation must continue to block the same routes whether an
application is online or offline.

## Acceptance scenarios

1. Connect an application, collect a workflow and its steps, then disconnect all
   executors. The app remains discoverable and its saved details show timestamps.
2. Repeat without opening the UI before disconnecting. If background collection
   is selected, eligible data is still available within the stated coverage.
3. Lose one of several executors, replace an executor, and reconnect after full
   scale-down. Live counts remain correct and older responses cannot regress
   newly collected data.
4. Restart Maestro while the application remains offline. With retained storage,
   saved data remains readable and no persisted executor appears online.
5. Request uncaptured, expired, oversized, or partially collected data. Report
   the actual coverage rather than a false empty result or complete history.
6. Reconnect and receive a privacy refusal or malformed response. Surface the
   failure without returning old data as a successful live read.
7. Exercise two applications with the same workflow ID and deployments sharing
   storage. Records remain isolated and gateway restrictions still apply to
   every existing route used for offline navigation.
8. Expire records or make storage unavailable. Saved reads do not extend TTL;
   live reads, commands, and recovery retain their existing behavior.

Use the existing Go and executor fixture tests for these behaviors, plus a
restart test against the selected backend. Reuse the existing SDK acceptance
tests to check that collection respects supported reads and privacy refusals.

## Decisions to settle

- Capture model: background collection plus live reads, or only requested data?
- Data scope: existing inspection data or external application logs as well;
  payloads, related data, and queue/schedule/overview coverage?
- Storage: SQLite or Valkey first; opt-in behavior and purge mechanism?
- Limits: acceptable freshness, workflow discovery coverage, retention durations,
  payload/page limits, and behavior at storage capacity?
- Offline API contract: supported search filters, freshness/coverage headers,
  and missing-data responses without breaking current clients?
